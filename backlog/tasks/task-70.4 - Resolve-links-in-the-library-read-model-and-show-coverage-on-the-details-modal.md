## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Stage 3 of TASK-70. Answers point 4 and makes a link visible in the library rather than only on the Same Game screen.

**Resolve at the chokepoint, and only there.** `LibraryQueryRepository.GetOwnershipBucketsAsync` gains a resolved work id, computed in the same pass that already runs demo consolidation and the non-game filter. That one query feeds the grid, the rail bucket counts, the All Games count, the filter panel options, list counts, the recommender candidate set, the feed and the account-visibility hidden count, so teaching it once teaches all of them. This stage does not change the grid grain: it still renders one tile per ownership, so no count moves and no bucket moves. What changes is that both store entries of one game now read the primary title and the primary cover, which is the visible half of the fix.

**Feed suppression resolves.** `feed_verdicts` and `feed_surfacings` are keyed by release. Dismissing the Steam entry of a game must suppress the Epic entry, or the feed will offer the same game twice under two store badges. Read them as any release under the resolved work.

**Details modal gains coverage.** An Also covers section on the game details modal lists every work linked into this one, each with its store badge, its own playtime, its own last-played and its per-release achievement rows, which is section 6.2 rendered literally for the first time. Each row carries a Separate this control that retracts just that link, so unlinking is available where the user notices the problem rather than only on a review screen.

**Do not resolve, and assert it.** `GetFacetTargetsAsync`, `WorkEnrichment`, `ProvisionalNameTarget`, `WorkRepository.GetAllAsync`, `update_acknowledgements`, `achievements`, `achievement_unlocks`, `IStoreTitleCounts` and `list_items` must keep reading unresolved, each for the reason recorded in TASK-70. Add an architecture test that enumerates the surfaces which read `works` or `ownerships` and asserts each is on the resolve list or the do-not-resolve list, so a new surface added later cannot silently join neither.

**Tests.** Two ownerships of one linked game render two tiles, both titled with the primary name and both drawing the primary cover. Bucket counts, All Games and the store title counts are byte-identical before and after linking. Dismissing one store entry in the feed suppresses the other. The details modal lists the covered titles with their own playtime and their own achievement rows, and never a blended percentage. Separate this retracts one link and leaves the rest of the act intact. Enrichment still targets the child work after it is linked. The architecture test fails when a new query reading `works` is added to neither list.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. CHOKEPOINT. LibraryQueryRepository.QueryAsync gains a resolved CTE over identity_links WHERE retracted_at IS NULL AND kind = @SameGameKind, bound from IdentityLinkKinds.SameGame so an expansion link cannot move a number, plus one LEFT JOIN. Cover key is overridden ONLY when the row's work is a child; an unlinked row keeps its exact per-release key, which is what keeps byte-identity honest rather than merely likely.

RecommendationEngine widens verdicts by resolved work instead of identity.WorkId, and keys storesByWork by resolved work so a linked cross-store pair keeps the bought-twice signal the destructive merge used to give it. THE RESOLVE INVENTORY AS BUILT. Five sites resolve. (1) LibraryQueryRepository.QueryAsync, the chokepoint: a same_game CTE over identity_links WHERE retracted_at IS NULL AND kind = @SameGameKind plus one LEFT JOIN, and OwnershipBucket gains WorkId, ResolvedWorkId and IsLinkedChild. Every surface it feeds inherits resolution: the grid, the rail bucket counts, All Games, the filter options, list counts, the recommender, the feed and the account-visibility count. (2) LibraryViewModel.LoadAsync, the display title and cover. (3) RecommendationEngine.AssemblePoolAsync, feed suppression and the bought-twice signal. (4) and (5) MergeQueueViewModel.DescribeAsync and DescribeWorkAsync, which render members MergeGrouping already resolved in 70.3. The sweep and SoftMatchAdmission were taught to resolve in 70.3 and were left alone.

DO NOT RESOLVE, and the reason each keeps, recorded in a comment at the site rather than only in this list. GetFacetTargetsAsync, WorkRepository.GetAllAsync / GetEnrichmentTargetsAsync / GetProvisionalNameTargetsAsync / ApplyEnrichmentAsync: resolving starves the child, and the child's own igdb_id is what fills the group; works.igdb_id is UNIQUE so under the destructive model only one row of a pair could hold it, and the whole point of the link is that both rows survive and both keep being enriched. UpdateAcknowledgementRepository: a Steam build acknowledged is not an Epic build acknowledged; the two stores ship different builds on different days, so a widened acknowledgement would mark read a patch the user cannot see. AchievementQueryRepository: 6.2 requires two sets, two rows, never blended, and this reader has no work join and no link join at all. IStoreTitleCounts: counts are per tile by design-system 11.2, and resolving would make the per-store numbers stop adding up to the library. GameListRepository / list_items: adding a game to a list is an explicit act on one store entry the user picked, so de-duplicating would remove a row somebody put there by hand. ReleaseRepository.GetIdentitiesAsync: the release-to-work map the resolvers are themselves built on, so resolving would be circular. The three OwnershipRepository reads and OwnershipAccountRepository.GetAccountRefsAsync: ownership is per store by the four-layer model and a link folds works, never ownerships. FeedFeedbackRepository.GetEndorsementsAsync: an endorsement records a launch that actually happened on one entry. LibraryHistoryStatsRepository.GetAsync: buying the same game on two stores is two purchases, and a year in review that folded them would report something that did not happen. PollCandidateSource.GetEligibleAsync: a poll target, per release. IdentityLinkRepository.AssertWorksExistAsync: the link machinery itself. MergeExecutionRepository (five members) and MergeUndoRepository.LoadLogAsync: the destructive executor, which moves stored rows and must see them as stored, and which keeps working until 70.7. MergeQueueViewModel.BuildLinkHistoryAsync: the history names each work by ITS OWN name, and resolving would print the parent's name on both sides of every row. Plus the ingest and monitor readers: EnrichmentSyncService.EnrichAsync, SampleDataSeeder.SeedLibraryAsync, SteamAccountPageImportService.BuildIndexAsync, SteamPlaytimeBackfillService.OwnershipAsync and SteamAccountsAsync, GameExecutableIndexBuilder.BuildAsync, ExternalIdResolver.PromoteProvisionalNameAsync.

THE ARCHITECTURE TEST, and its shape. tests/Winnow.Tests/IdentityReadInventoryTests.cs. It scans src/**/*.cs and finds two kinds of reader: a SQL statement matching FROM or JOIN over works or ownerships, and a call to a read member (Get/Find/Count/List/Any/Exists) through an identifier declared as IWorkRepository or IOwnershipRepository. Writes are deliberately not readers -- the inventory is about the READ model, and an INSERT is not a place identity can be shown wrong. Each site is keyed by file plus ENCLOSING MEMBER, found by walking up to the nearest declaration line, so the key survives edits inside a method and a rename is caught as a new reader rather than silently accepted. It found 34 sites and all 34 are classified.

IT NAMES THE CALL SITE. Failure prints one line per hit: file(line) :: Member -- what matched -- the matched text, under an instruction naming the two lists and the file to edit. Three assertions, not one. Every reader is classified. The inventory names no reader that no longer exists, so the list cannot rot into places that used to matter. And two NEGATIVE CONTROLS scan a synthetic directory containing a new reader and assert it is caught and that the message names it: one for a new SQL query, one for a new view model reading _works.GetAllAsync, which is the surface the design actually worried about. Without those the first two tests only prove that a list agrees with itself today.

THE REPOSITORY ROOT IS STAMPED AT BUILD TIME. Winnow.Tests.csproj writes an AssemblyMetadata attribute holding the repository root, because walking up from the test binary cannot find the source tree: the build runs into an artifacts path while the user holds src/Winnow.App/bin, so the assembly does not sit under the repository at all. A missing root fails the test loudly rather than skipping it -- a skipped architecture test is not a guard.

MEASURED COST OF RESOLUTION. 1,000 games, 1,000 ownerships, 200 same-game links (a fifth of the library cross-store, far past anything the author's library holds). Warm, unresolved: 11-12 ms. Warm, resolved: 17-19 ms. Cold first query in the same fixture: 37 ms. So the join adds roughly 6 ms to a query that runs once per library load, against a page the user is already waiting on for cover art. The join multiplies nothing -- 1,000 rows in, 1,000 rows out, 200 of them children -- which is the property the test actually pins, alongside a deliberately loose 2 s ceiling that a cartesian blow-up or an accidental per-row read could not pass. The design asked for this to be measured rather than assumed; measured, it does not change the recommendation.

WHAT THE MODAL SHOWS. A new ALSO COVERS section, first in band 4 and drawn only when this game covers another title. A composite TOTAL at the top: minutes summed across every entry in the group with its OWN coherent last-played, the latest anywhere in the group. Then one row per store entry -- the primary's own first, then the covered titles -- each carrying its own store badge, its own playtime, its own last-played, and its own per-release achievement row (unlocked/total and that release's own percentage). The per-store rows are the breakdown the user's decision of 2026-08-31 requires so the composite can be checked against its parts. Each covered row carries Separate, which retracts just that link.

THE F10 HAZARD, MADE STRUCTURAL RATHER THAN REMEMBERED. CoveragePlaytime has a private constructor and no settable members. The only way to obtain one is Across(entries), which derives the minutes and the date from the same set in one pass. A sum paired with a foreign store's date is not a mistake that can be made; there is no constructor that would express it. The test that holds it seeds the higher-playtime entry with the OLDER date, so a composite that borrowed a date from a store would visibly show the wrong one.

EXPANSIONS CANNOT MOVE A NUMBER, TWO WAYS. At the type level: IdentityCoverage.For takes a SameGameResolution, and ExpansionGrouping has no Resolve method at all, so an expansion grouping cannot be passed into a position that computes a number. At the query level: the bucket query's kind filter is bound from IdentityLinkKinds.SameGame, not written as a literal. An_expansion_link_moves_nothing seeds the Civilization IV case and asserts the expansion stays its own title, stays never_played, and never enters the coverage sum -- before the stage that creates expansion links exists.

ACHIEVEMENTS, AND 6.2 RENDERED LITERALLY FOR THE FIRST TIME. The tables have been in 0001 since the beginning and nothing had ever read them. New IAchievementQueryRepository / AchievementQueryRepository: GROUP BY release_id and by nothing else, no work join, no link join. ReleaseAchievementSummary describes exactly one release and there is no type, method or property anywhere that combines two of them, which is what stops a blended percentage from being written by accident rather than by a rule somebody has to remember. The test seeds 10/10 on one platform and 3/10 on the other and asserts two rows, 100% and 30%, and that the blend 6.2 forbids (65%) appears nowhere.

SEPARATE THIS. New IIdentityLinkRepository.RetractLinkAsync(childWorkId): the act retraction narrowed to one child, not a second mechanism. It stamps that child's one live link under a new unlink act (ux_identity_links_live makes the singular read a schema fact) and restores the link that this child's link displaced, keyed by retracted_by_act_id plus child_work_id -- the same promise RetractActAsync makes, at the grain of one child. Other children the act displaced are left alone, because their links still stand and restoring them would put a work under two parents. Retracting twice returns false and writes nothing.

ONE TEST FROM 70.2 WAS REWRITTEN, DELIBERATELY. IdentityLinkTests.A_live_link_changes_no_bucket_row asserted Assert.Equal(before, after) on the whole row, which was the correct inertness proof while nothing read a link and is exactly what this stage ends. It is now A_live_link_moves_the_resolved_work_id_and_nothing_else, comparing every row field by field with ResolvedWorkId held aside, then asserting that the one column that exists to move moved exactly where it should. The claim got sharper rather than weaker.

DISPLAY RESOLUTION IS GUARDED SO NOTHING MOVES WHEN NOTHING IS LINKED. In LoadAsync the row keeps its OWN work for everything enrichment reads and gains a separate display work. Cover art is borrowed ONLY when the row's work is a child; an unlinked row keeps its exact per-release cover key. That guard is what makes byte-identity structural rather than lucky -- taking a work-level cover key unconditionally would have changed which key a multi-release work's second release drew, with no link anywhere.

THE RECOMMENDER TAKES NO NEW DEPENDENCY. It reads the resolved work id off the bucket rows it already reads, so the feed and the grid cannot disagree about what one game is, and there is no second read of the link table to fall out of step. storesByWork is keyed by the resolved work as well, because a same-game link is the statement the destructive merge used to make by putting both releases under one work; resolving there keeps the bought-twice signal the merge gave it.
