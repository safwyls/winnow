## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Stage 4 of TASK-70. The second half of point 3: presenting a base game with its expansions as one group. It uses the same table as same-game linking and deliberately none of its semantics.

**The relation is not the same fact.** Steam Prey and Epic Prey are one game sold twice; Civilization IV and Beyond the Sword are two products where one depends on the other. `expansion_of` therefore changes no count, no playtime, no bucket and no recommendation. It groups for display only. Summing 30h of the base game with 120h of an expansion produces a number no source reported about either, and folding an unplayed expansion into a played parent would delete what is probably the best recommendation the app can make: you played this for two hundred hours and never opened the expansion. If a later product decision wants a rolled-up figure, it is an additional derived number shown beside the two real ones, never a replacement for them.

**A separate detector, because the soft matcher will not find these.** The matcher scores title distance, and Civilization IV against Civilization IV Beyond the Sword is not a near-title match. Propose expansions by normalised-title prefix containment (the child normalises to the parent tokens plus a suffix), gated on shared publisher and year proximity, and never auto-applied.

**The population is small and known.** Epic DLC and GOG DLC never reach the database: `EpicLibrarySource` skips entries with a non-empty `mainGameItem.id` and `GogLibrarySource` skips entries where `GameId` differs from `RootGameId`. Steam DLC generally has no separate library entry. So the candidates are Steam appids Valve types as games whose titles extend another owned title. Size the feature to that; do not build a general DLC subsystem.

**Presentation.** A group card in the same grammar as the same-game card: the base game, its proposed expansions, a checkbox each, applied as one act. On the game details modal, an Expansions section listing the children with their own playtime and last-played, stated as separate products. In the library grid, an optional setting groups expansions under the base game; off by default.

**Tests.** An expansion link changes no bucket count, no All Games count, no store title count and no playtime figure anywhere. The recommender still scores and can still recommend an unplayed expansion whose parent is played out. The detector proposes Civilization IV with its expansions and does not propose two unrelated titles sharing a first token. Applying a group of six is one act with one undo. The details modal lists expansions separately from covered titles, and the two sections are never merged.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. DETECTOR (pure, Core, BCL-only). New Winnow.Core/Identity/ExpansionDetector.cs over a plain ExpansionSubject (work id, title, year, publisher). Rule: the child's normalised token list must have the base's token list as a STRICT ORDERED PREFIX. False-positive guards, each stated at the site: (a) the suffix may not BEGIN with a number token, which is what separates Portal / Portal 2 and Witcher / Witcher 3 Wild Hunt from Civilization IV / Civilization IV Beyond the Sword; (b) rebuild-edition markers must agree, so Skyrim / Skyrim Special Edition is a rebuild and not an expansion; (c) a KNOWN publisher mismatch vetoes; (d) known years must not put the child BEFORE the base, nor further after it than MaxYearGap; (e) a minimum base core length; (f) at least one corroboration must fire - publisher known and equal, both years known and inside the window, or a separator boundary in the child's RAW title whose left side normalises to exactly the base core (Civilization IV: Beyond the Sword). A pair with no corroborating evidence is not proposed. Each child takes at most one base: the LONGEST matching prefix, lowest work id on a tie. Edition-only extensions collapse to an equal token list and therefore never propose.
2. POPULATION. New Winnow.Resolve/LibraryExpansionScan.cs. Reads release identities, drops non-games and provisional names exactly as the soft-match sweep does, folds releases to works, resolves work ids through the live SAME-GAME map, and skips a pair that is already linked either way, a child that already has a live parent, a base that is itself a live child, and any pair the user has refused. Writes nothing.
3. REFUSALS ARE STORED, PROPOSALS ARE NOT. Migration 0020_expansion_refusals.sql, additive: one small directional table (base_work_id, child_work_id, refused_at, note) with a unique pair index. Proposals stay DERIVED for the same reason buckets are - thresholds get tuned and stored proposals rot - while a refusal is a decision the user made and decisions are stored. New IExpansionRefusalRepository / ExpansionRefusalRepository.
4. THE 70.3 CARD DOES NOT FIT, AND A SECOND ONE IS BUILT. Stated honestly rather than forced: a same-game group is N peers of one game whose primary is a CHOICE, and the KEEP radio is that choice; an expansion group is one base plus N extensions whose parent is STRUCTURALLY determined by the relation, so a radio there would let the user assert that Civilization IV is an expansion of Beyond the Sword. The evidence is different too (prefix and corroboration, not the matcher's four-signal diff). New ExpansionGroupViewModel / ExpansionMemberViewModel reuse the GRAMMAR - MergeSideViewModel faces, 200x300 base capsule, 64x96 roster chips, include checkboxes, one act, retractable - and drop the radio and the signal table. It ships as a third segment, REVIEW / EXPANSIONS / HISTORY, because the question and both answer verbs differ from Same game / Different games.
5. RENDERING, FOLLOWING 70.4'S COVERAGE TREATMENT. New GameExpansionsViewModel: an EXPANSIONS section on the base game's modal listing each expansion with its OWN playtime and last-played and a Separate control, and an EXTENDS line on an expansion's own modal naming what it extends. Deliberately NO composite total, which is the visible difference from ALSO COVERS and the thing that makes the no-roll-up rule legible on screen. The two sections are separate and never merged.
6. RETRACTION. Reuses RetractLinkAsync (one child) and RetractActAsync (the whole group), both shipped in 70.2/70.4. The link history rows become kind-aware so a grouped act does not read as a same-game link.
7. ONE DEFECT FOUND AND FIXED. IdentityLinkRepository.LinkAsync re-parents the children of a work that is becoming a child, but inserts them with the REQUEST's kind. With only same_game live that was invisible; with expansion_of live it silently converts an expansion into an identity and moves playtime. Displaced links now keep their own kind.
8. TESTS. An expansion link moves no number: library count, every bucket count, both playtimes, the grid's tile count, the per-store title counts, and the recommender pool, asserted before and after. An unplayed expansion of a played-out parent is still reachable by the recommender. The detector proposes a real base-plus-expansion pair and refuses two unrelated titles sharing a first token, a sequel, and a rebuild edition. Retract and re-link repeatedly. The 70.4 architecture test still passes, with every new reader classified in its inventory.
9. OUT OF SCOPE, STATED: the optional grid grouping setting (this subtask's AC #6). The brief for this stage says an expansion link must not move a tile's collapse, and the tests demand an unchanged tile count, so no grid setting is built and AC #6 stays unchecked.
10. Scoped tests, then the full suite, built via --artifacts-path into the scratchpad. Prose by docs-writer. Nothing committed, task not finalized.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
IMPLEMENTED, not finalized. Full suite green. Not committed. The live database was never opened and the user's running app was never touched.

THE DETECTOR, AND WHY IT HAD TO BE A SECOND ONE. New pure BCL-only src/Winnow.Core/Identity/ExpansionDetector.cs over a plain ExpansionSubject (work id, title, year, publisher). The soft matcher scores title DISTANCE, so "Civilization IV" against "Civilization IV: Beyond the Sword" is a bad match at any threshold; this asks a different question, does one title EXTEND another, and answers it by strict ordered token prefix over TitleNormalizer's output. Never auto-applies anything.

THE FALSE-POSITIVE GUARDS, each a named ExpansionRefusalReason rather than a score falling below a line. (1) SequelOrdinal: a suffix that OPENS on a number is refused, which is the single most dangerous case a prefix rule has — "Portal" prefixes "Portal 2" exactly, and "The Witcher" prefixes "The Witcher 3: Wild Hunt". "Half-Life 2: Episode One" survives because its suffix opens on "episode". (2) RebuildEdition: markers must agree, so a remaster is a separate build and not an extension (SS9 pitfall 5). (3) PublisherMismatch: a KNOWN mismatch vetoes; unknown does not fire. (4) ChildPredatesBase: an expansion does not ship before its base, with one year of slack because two rows are enriched from different sources and a regional date can disagree by a year. (5) YearGapTooWide, default 15. (6) BaseTooShort: a floor on the normalised CORE, so it is a floor on what was actually compared. (7) NoCorroboration, which is the guard that does the real work: the prefix alone is a coincidence waiting to happen — "Rush" prefixes "Rush Bros" — so at least one of publisher-known-and-equal, both-years-known-inside-the-window, or a SEPARATOR BOUNDARY must fire.

THE SEPARATOR BOUNDARY, WHICH THE DESIGN DID NOT ASK FOR AND THE FEATURE NEEDS. The child's RAW title cut at a colon, dash, pipe or slash whose left side normalises to exactly the base core. It is the only corroboration that needs no enrichment, so a library the metadata backfill has not reached still gets its real Steam pack entries, which nearly all carry one. EVERY separator position is tried and not just the first, or the hyphen inside "Half-Life 2" would decide the question and "Half-Life 2 - Episode One" would lose its strongest evidence.

TWO PROPERTIES THAT FALL OUT. Each child takes at most ONE base — longest matching prefix, lowest work id on a tie — so a library holding both "Civilization" and "Civilization IV" files a Civ IV pack under the nearer, and the queue never asks one question twice. And an edition bundle proposes NOTHING, because the normaliser lifts "Complete Edition" out of the core and "Civilization IV: Complete Edition" then has the same token list as its base, so there is no extension to find.

PROPOSALS ARE DERIVED; ONLY REFUSALS ARE STORED. New src/Winnow.Resolve/LibraryExpansionScan.cs re-derives the proposals on every pass, for exactly the reason SS6.1 gives about buckets: the guards get tuned and a stored proposal computed under last month's rules rots. A refusal cannot be re-derived — it is a decision a person made about two specific titles — so it goes in migration 0020's expansion_refusals, directional, with a unique pair index and INSERT OR IGNORE so answering twice is a no-op that keeps the FIRST refused_at. The affirmative answer is NOT in that table: it is an identity_links row at kind expansion_of, and a proposal is answered affirmatively if and only if such a link is live, which is the one-home rule 0019 applied to same-game answers. The scan also drops non-games and provisional names exactly as the sweep does, folds releases to works at the RESOLVED work id, and skips a pair already grouped either way, a child that already has a live parent, and a base that is itself a child.

THE 70.3 CARD DID NOT FIT, AND I SAY SO RATHER THAN FORCING IT. Two structural reasons, not aesthetic ones. FIRST, the KEEP radio means something different: on a same-game card either title could be the one the library shows, so the primary is a genuine choice; on an expansion card the parent is fixed BY THE RELATION — the base is the title the others extend — so the same control would let a user assert that Civilization IV is an expansion of Beyond the Sword. SECOND, the evidence is different: the four-signal diff scores distance between two titles, which is precisely why it cannot find these pairs at all, so a card built around it would show the user the wrong reasoning. New ExpansionGroupViewModel / ExpansionMemberViewModel therefore reuse the GRAMMAR and not the card — the same MergeSideViewModel faces, a 200x300 base capsule beside 64x96 roster chips, include checkboxes for none/some/all, one act, one retraction — and drop the radio and the signal table. ExpansionMemberViewModel has no IsPrimary at all, so asserting the wrong direction is not a mistake the type can express.

WHERE IT LIVES, AND THE DEFAULT THAT DIFFERS. A third segment, REVIEW / EXPANSIONS / HISTORY, rather than a third kind of card in one scroll: the two surfaces take different answers (Same game / Different games against Group / Not expansions), and interleaving them would give S and D two meanings. The expansion surface has its own keys, G and N, with Enter grouping. Members arrive CHECKED, which is the opposite of 70.3's roster default, and the reason is the reason 70.3 gave for its own: an unchecked same-game default guards TRANSITIVITY, stopping a connected component's closure asserting what no single proposal did, and an expansion proposal is one direct already-corroborated claim about one pair with no closure to guard.

WHAT THE MODAL SHOWS, BOTH WAYS. On a base game: an EXPANSIONS section following 70.4's coverage treatment — one row per pack, each with its OWN playtime beside its OWN last-played, store chips, and an Ungroup control. On a pack: an EXTENDS line naming the base with the same control, so the grouping comes apart from either end. THE ONE DELIBERATE DIFFERENCE FROM ALSO COVERS IS THE ABSENCE OF A TOTAL, and it is the whole feature made visible: coverage sums because two store entries are one game being played, expansions do not because they are separate products and the sum is a figure no source reported about either. There is no property on GameExpansionsViewModel or its row that adds two rows together and no CoveragePlaytime spanning the section. The two sections are separate and never merged; a test seeds a game that has both and asserts they hold different things.

PROOF THAT NO NUMBER MOVES. ExpansionLinkTests.An_expansion_link_moves_no_number_anywhere loads the whole library view model before and after a grouping and compares a snapshot of every figure on screen — tile count, All Games, TotalCount, every rail bucket count, every per-store title count, and each game's own playtime, bucket and last-played — as one string, so a figure added later is covered without anyone remembering to add it here. It then states the same positively: two tiles, the pack still never_played at 0 minutes, the base still at 12,000. Below that, the bucket query resolves every row to itself; the coverage sum cannot see the expansion at all; and in Winnow.Recommend.Tests an unplayed pack of a played-out base is still in the feed after grouping, with the item list and every score identical before and after.

TWO DEFECTS FOUND, BOTH OF WHICH WOULD HAVE MOVED A NUMBER. FIRST, IdentityLinkRepository.LinkAsync re-parents the children of a work that is becoming a child, and it wrote those displaced links under the REQUEST's kind. With only same_game live that was invisible; the moment an expansion exists, holding Civilization IV as one game with its GOG twin would have converted its six packs into same-game links and folded six playtimes into one. A displaced link now keeps its OWN kind, covered by Re_parenting_a_base_game_keeps_its_expansions_expansions. SECOND, the mirror case: an expansion_of act whose child is itself a live parent would re-parent that child's same-game twin onto the BASE game. Re-parenting is right for same_game, where it keeps one statement true, and wrong here, so it is now refused by name — new IdentityLinkRefusal.ExpansionChildIsAlreadyAParent — rather than repaired. The scan does not offer the question either, so the refusal is a backstop and not the user's experience.

VERIFIED THAT 70.4'S FILTER STILL HOLDS. The bucket query's kind filter is still bound from IdentityLinkKinds.SameGame and not written as a literal; IdentityCoverage.For still takes a SameGameResolution and ExpansionGrouping still has no Resolve; LibrarySoftMatchSweep, LibraryViewModel and RecommendationEngine still resolve the same-game half only. LibraryViewModel now reads the expansion half into a SEPARATE field of a different type, which is what stops it reaching anything that computes a number. IdentityReadInventoryTests passes unchanged and needed no new entries: nothing added here reads works or ownerships.

DEPENDENCIES MADE REQUIRED, ON 70.3'S OWN RULE. MergeQueueViewModel takes LibraryExpansionScan and IExpansionRefusalRepository as required parameters, because a type registered in the container and resolved nowhere is indistinguishable from one that works. Four test fixtures were adapted and MergeScreenRegistrationTests now builds the expansion half too.

NOT BUILT, DELIBERATELY: this subtask's AC #6, the optional setting that groups expansions in the library grid. The brief for this stage says an expansion link must not move a tile's collapse and the tests demand an unchanged tile count, so no grid setting exists and expansion links collapse nothing. AC #6 is left unchecked and is the one criterion this implementation does not address.
