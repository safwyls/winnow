## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The Stores screen currently offers only a Web API key for Steam authentication. This task restructures the Steam connection to present two peer methods, following Playnite's model: the existing Web API key, and a new embedded WebView sign-in. The WebView path would give Winnow the user's Steam identity directly (enabling the account visibility toggle without waiting for a Year-in-Review disclosure call to confirm the account), support keyless operation, and allow purchase-history capture in the same session. A prerequisite research spike must determine whether the WebView session can mint a `webapi_token` usable against the two endpoints Winnow depends on (`GetUserYearInReview`, `ClientGetLastPlayedTimes`), or whether a durable session is required. The spike's findings gate the design and will require a recorded revision of the section 4.7 amendment's binding conditions either way. Winnow must prompt for explicit permission before capturing purchase history during a WebView sign-in; declining the prompt leaves the sign-in fully functional for identity and playtime backfill.
<!-- SECTION:DESCRIPTION:END -->

- [ ] #5 The design lands only after the token-viability spike's findings are recorded in docs/spikes and its conclusions reviewed

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Credential seam. Introduce SteamCredential, ISteamCredentialProvider, and SteamCredentialSelector; convert the three hand-concatenated key= call sites in SteamHistoryClient and SteamWebApiClient to a single AppendTo. No behaviour change, key-only path works exactly as today. Unblocks every later stage by giving credentials a uniform shape.

2. Session storage. DPAPI-protected, settings-backed session store mirroring the Epic precedent with distinct entropy. Persists access token, expiry, audience, issuer, steamid, refresh token, and renewal bookkeeping; stores no cookie, no password, no page content. A session provider handles load, expiry, and lapse but not renewal. The section 4.7 second amendment lands here because this is where a durable credential first touches disk. Unblocks sign-in by giving it somewhere to write.

3. Sign-in session. ISteamSignInSession contract in Core and WebView2SteamSignInSession promoted from the verified probe. The mint-scope predicate moves into SteamAccountPagePolicy as a third narrower tier beside the harvest predicate. Probe scaffolding and its command-line switch are deleted. Unblocks identity unification by producing a token with a subject claim.

4. Identity unification. Extract one shared account-confirmation writer used by both the key path and the sign-in path. Generalise the credential fingerprint without changing the existing key digest. Sign-in writes the owned account immediately from the token subject; the key path's disclosure refetch is kept unchanged for key-only users. Acceptance criterion 4 lands here. Unblocks the stores UI by making both paths converge on a single account record.

5. Stores UI. Both connection methods presented with honest copy, sign-in first and key as a genuine alternative including in-app key input. Sign-in and sign-out commands, session health rendering, and the purchase-history permission control whose decline leaves sign-in fully functional. Acceptance criteria 1 and 2 land here. Unblocks renewal by surfacing the health state it will maintain.

6. Renewal. The finalizelogin and transfer_info exchange plus token mint, single-flight with rotation handling, failure classification separating hard lapse from transient, health transitions surfaced before the token dies, and scheduler integration. This is the riskiest stage and rests on untested refresh assumptions, which is why it is last: without it a signed-in user still has roughly a day of access and one-click re-sign-in, and keyed users are unaffected.

UseCookies=false and AllowAutoRedirect=false on the primary handler, so steamLoginSecure is read out of Set-Cookie into a local variable, sent once on the mint request, and never touches a cookie jar or disk. SteamSessionProvider gains IsRenewalDue plus a RenewAsync(stale) that follows EpicTokenProvider: single-flight on the existing SemaphoreSlim, another caller's already-refreshed result handed back rather than the refresh token spent twice, rotation stored atomically with the new access token, and the lapse latch consulted so a rejected token is not respent. SteamCredentialProvider decides whether renewal may block: an Unattended pass with a usable API key returns the key WITHOUT consulting the session at all, which is what structurally guarantees a renewal can never delay a scheduler tick. Reactive renewal is one retry on a 401 at the two client send paths, via a new ISteamCredentialProvider.RenewAfterUnauthorizedAsync; SteamWebResilienceHandler does not retry 401, which is what makes it a clean trigger. SteamWebResilienceHandler gains buffer-and-clone (SteamRequestReplay, mirroring the IGDB precedent) because the renewal requests are POSTs and a spent content stream cannot be replayed. Classification: 401/403/400 and an AccessDenied-family eresult are Rejected (hard lapse); network, timeout, 429 and 5xx are Transient; an unreadable or reshaped body is Transient rather than a sign-out. A hard lapse drops the refresh token, records the failure and latches, keeping the record on the books so the screen still says 'your sign-in ended' rather than 'never connected' - the eleven-key stored shape is unchanged because refresh_token is already nullable and always emitted. An audience change or a subject change after a renewal lapses rather than loops; the issuer is deliberately not compared because the live evidence shows it varies per mint.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Spike complete (docs/spikes/steam-web-session-auth.md, 2026-08-30). Verdict: a session-minted access token works for all three endpoints Winnow uses and is better behaved on failure than the API key (a bad token returns a hard 401; a bad key returns a silent 200 with an empty envelope). Evidence includes Valve's own shipped store bundle reaching GetUserYearInReview with access_token and no key, and Playnite's source carrying literal key/token pairs for the same methods. The token is a JWT living about a day; renewal needs live cookies or the steamRefresh_steam refresh token (~207 days with remember-me). User decisions 2026-08-30: (a) persist the refresh token under DPAPI so WebView sign-in becomes a true peer for unattended scheduled work, which requires its own recorded section 4.7 amendment covering a long-lived credential; (b) verify live before building the full design, specifically that a real store-minted token returns populated data for the user's account and that Steam sign-in completes inside the off-the-record WebView2 (Steam Guard, possible hCaptcha). A probe path lands first; the design follows the probe's findings.

Decision note, 2026-08-30, recorded after the TASK-56 live probe proved a WebView sign-in mints a working webapi_token, that the token returns populated data from all three endpoints Winnow uses, and that it resolves the signed-in account exactly (page steamid and JWT sub agree). Evidence: docs/spikes/steam-web-session-auth.md section 7.1.

1. Presentation order. WebView sign-in is presented as the fuller path: account identity at mint time (no Year in Review disclosure refetch), purchase history capture in the same consented session, and no key registration outside the app. The Web API key is the alternative, not a fallback, offered for users who prefer not to sign into Steam inside a third party app. Both remain genuinely usable and the UI must state plainly what each gives up. Sign-in gives up unattended durability: the minted token lives about a day and scheduled work depends on refresh renewal succeeding silently. The key gives up immediate identity, purchase history capture, and the token-only services, and requires registering a key on Steam's site. The presentation must be honest rather than burying the key.

2. Credential assignment for unattended schedulers. When both exist, the key drives the 15 minute local pass and the 6 hour remote pass; the session is the fallback for keyless users. Reason: the key does not expire and needs no renewal. The token lives about a day (24h 22m measured 2026-08-30) and renewal depends on the persisted refresh token and Valve's jwt/finalizelogin endpoint. A renewal failure overnight costs a sync cycle the user cannot intervene in; the key has no such failure mode.

3. Standing decisions, unchanged, each needing recorded follow-through. (3a) The steamRefresh_steam refresh token is persisted under DPAPI CurrentUser scope, the same protection DpapiEpicSecretProtector applies to the Epic refresh token, so the access token can be re-minted silently and the session can serve scheduled work. This is a section 4.7 amendment: condition 1 currently forbids persisting session material, and a long-lived bearer credential at rest is exactly what it was written to prevent. The amendment must be recorded in ROADMAP.md with its own binding conditions before the implementation ships. (3b) Purchase history capture during a sign-in requires an explicit permission prompt; declining leaves the sign-in fully functional for identity and playtime backfill.

4. Consequence to design around: the keyless signed-in user. They get account identity and the account scope filter immediately, on demand syncs and backfills immediately, the token-only services immediately, and unattended scheduling only for as long as refresh renewal keeps working. That last point is fragile: a refresh token can be invalidated by signing in elsewhere, one contrary community report exists against the finalizelogin route, and the long lifetime applies only if the user chose remember me. The design must make that state legible rather than silently degrading. When renewal fails the UI surfaces it promptly with a one click re-sign-in and explains that adding an API key makes scheduled syncs unconditionally reliable. A silently dead credential that drops sync cycles without telling the user is the failure mode to avoid.

S5 (Stores UI) implemented 2026-08-31. No DB migration. Acceptance criteria 1 and 2 land here. Not committed. S6 (renewal) remains.

**Presentation.** The Steam card on the Platforms screen now carries both methods, sign-in first as the fuller path and the Web API key second as a genuine alternative. Both get the same heading weight, the same two paragraphs (what it does, what it gives up) and the same primary button. Laid out down the card rather than across it (unlike the import screen's side-by-side peer grid) because each method here owns live controls and a state of its own. All user-facing copy lives in one new file, `src/Winnow.App/ViewModels/SteamConnectionCopy.cs`, following the `SteamAccountImportCopy` precedent so the two methods' honesty can be reviewed together rather than scattered through a view model.

**The key finally has an input.** Before this stage the screen only hinted at a `Steam__ApiKey` environment variable, so offering the key as a peer was not honest. It now has a masked field (`TextBox.PasswordChar`), Save, Clear, and a button that opens `https://steamcommunity.com/dev/apikey` through the existing `IUriDispatcher`, still the one place a URI leaves the application. Saving writes `steam.api_key` through `ISettingsRepository`, then calls `ISteamCredentialProvider.Invalidate()`, because `ChainedSteamApiKeyProvider` memoises (a key is read on every enrichment call) and a key that needed a restart to take effect is a field that reads as broken. Reconciliation (`ISteamAccountConfirmation.ReconcileAsync`) runs after the invalidate and in that order, because reconciliation asks which credentials are in force and that question has the wrong answer until the memo is dropped: a confirmation earned by the key just replaced or removed no longer names a credential present, and an account filter still trusting it would hide the wrong library. The field is emptied the instant the key is saved; a bound property with a public getter is no place for a bearer credential. The empty string is the cleared state rather than a deleted row, because `ISettingsRepository` has no delete and `SteamApiKey.TryCreate` already treats blank as unset, so an empty value and an absent row mean the same thing to every reader.

**Three key states, not two.** A key can come from the settings table (this screen owns it) or from `Steam__ApiKey` / `appsettings.local.json` (it does not). `SettingsTableApiKeySource.SourceName` and `ConfigurationApiKeySource.SourceName` were promoted to constants so "app-managed" is a comparison against a named value rather than a string literal match. Clear is DISABLED rather than hidden for a configuration key, and the status line has already explained why; a Clear that appeared not to work would be read as a bug. Saving is still allowed there, because the settings table is first in the chain.

S6 (silent session renewal) implemented 2026-08-31. No DB migration. No UI change: S5 already renders all six health states, and this stage is what makes `RenewalFailing` reachable. Not committed. Not finalized — the orchestrator runs the finalization pass.

**The renewal sequence, as implemented.** Three request kinds and no others (§4.7 second amendment, condition 3), all three living as URI constants in ONE file (`SteamSessionRenewer`) so an audit of the closed list reads one file. (1) `POST login.steampowered.com/jwt/finalizelogin` with the stored refresh token as `nonce`, a freshly generated `sessionid` sent as both form field and `Cookie` header (Steam's CSRF check compares the two), and a `redir` of the store login page. The refresh token travels in a BODY, never a URI, because a URI reaches the framework's own request logging. (2) The `transfer_info` POSTs that response returns, NARROWED to entries whose URL is an absolute HTTPS URI on `store.steampowered.com`; `help.steampowered.com`, `steamcommunity.com` and any plain-HTTP entry are ignored rather than requested, which is what stops a reshaped response body from directing Winnow's traffic. (3) `GET store.steampowered.com/pointssummary/ajaxgetasyncconfig`, a JSON endpoint, chosen over an authenticated HTML page precisely so no unattended request parses HTML. No browser at any point. `steamLoginSecure` is read out of `Set-Cookie` into a local string, sent once on the mint request, and dropped: the named client's primary handler is registered `UseCookies = false` (no cookie jar even in memory) and `AllowAutoRedirect = false` (a redirect is a request to a host the closed list did not name). Nothing from the exchange is persisted; the only write is the same eleven-field blob.

**Failure classification.** Rejected (hard lapse): 401, 403 or 400 at any step; a Valve EResult from the denial set {8 InvalidParam, 10 Denied, 15 AccessDenied, 26 Revoked, 27 Expired} in an `x-eresult` header or an `eresult` body field on a 200; a mint response that STATES `webapi_token` and leaves it empty, which is what pointssummary returns to a caller it does not consider signed in; a renewed token whose `sub` names a different account; a renewed token whose `aud` differs from the stored audience. Transient: network exception, timeout, 408, 429, every 5xx, any unrecognised status, an unparseable body, a body with no `webapi_token` field at all, a finalize response with no usable transfer target, and a renewed token that does not decode. NotRenewable: no refresh token, and no request is sent. Expired: the refresh token is past its own expiry, recorded as its own kind because that failure was predictable. The direction of doubt is chosen — being wrong toward Transient costs one skipped pass; being wrong the other way costs the user their session — which is why node-steam-session issue #56 (AccessDenied on every refresh route, 2026-05, unresolved) is planned for as a live possibility rather than a formality.

**The one place the instruction was read against its letter, deliberately.** The brief said a hard lapse should "clear the stored session". What ships discards the refresh token — from memory and disk, so no unspendable long-lived bearer credential is left at rest — and LATCHES the session off, but keeps the session record. A bare clear would take the Stores screen from "your sign-in ended, sign in again" to "you never connected", which is the distinction condition 8 makes load-bearing and which `SteamSessionProvider`'s own type comment already records as a standing decision. The result is an ordinary token-only session carrying a recorded failure: `Classify` reads it as `RenewalFailing` while the access token is still alive and `Expired` afterwards, so the warning arrives BEFORE the credential dies, and `RenewalFailing` becomes reachable exactly where it was written to be used. The stored key set is untouched because `refresh_token` is already nullable and always emitted.

**Single-flight and rotation.** `SteamSessionProvider.RenewAsync(staleSession, ct)` follows `IEpicTokenProvider.RefreshAsync` on the `SemaphoreSlim` the provider already holds. A caller whose session has already been replaced is handed the replacement and no request is sent. This is correctness, not politeness: spending a refresh token can invalidate the previous one, so a double spend is a self-inflicted sign-out. A rotated refresh token is written together with the access token it arrived with, in one `SaveAsync` of one blob, so there is no window in which they disagree; `WithRenewedAccess` recomputes `refresh_expires_at` from the NEW token rather than carrying over the old date, and a null rotated token means "Steam did not replace it", never "you now have none".

**Proactive and reactive.** Proactive when the access token is inside its renewal lead (one hour against a measured ~24 h 22 m token), using the same arithmetic `Classify` uses for `RenewalDue` so the state the screen shows and the work the provider does cannot disagree. Reactive is exactly one retry on a 401 at the two clients' new shared send path (`SteamAuthorizedRequest`), and the bound is structural — pass 0 may renew, pass 1 may not — rather than a counter. Verified and pinned: `SteamWebResilienceHandler` does not list 401 as transient (it retries 429, 408 and 5xx only), so a 401 reaching a call site is Steam's verdict rather than a blip the policy was still working through. That handler DID need one change: S6 puts form POSTs on the pipeline and a spent content stream cannot be replayed, so it now buffers and clones per attempt (`SteamRequestReplay`, mirroring the IGDB precedent). A GET buffers to null and clones to an equivalent message, which is why the existing SteamWeb tests pass unmodified.

**Scheduler integration, made structural rather than timed.** Decision note 2: the key drives the unattended 15-minute and 6-hour passes, the session is the fallback for keyless users. `SteamCredentialProvider.GetAsync` now returns the key immediately on an unattended pass WITHOUT consulting the session at all — not reading it, not renewing it, not waiting on it — so a renewal in flight, slow, or failing cannot delay a tick because the tick never reaches the code that would wait. A timeout would have been a promise about how long; this is a promise that it does not happen. The selector would return the same key from the same inputs, so the answer is unchanged; what changed is what it cost. `GetInventoryAsync`, which the Stores screen binds to, is likewise a plain non-renewing read (§5.1). There is deliberately no fire-and-forget background renewal: an unobserved task on a credential path was not worth the nondeterminism.
